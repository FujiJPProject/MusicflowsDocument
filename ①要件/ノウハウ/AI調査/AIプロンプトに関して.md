# AIプロンプトに関して

## 原則

### 1. 役割・目的・読者・ゴールを明示する

**理由：ユーザー側に必要な情報が示されやすい**

- 詳細
  - AIが「どの立場で、何を達成するために、どの粒度で答えるか」を判断しやすくなる。
  - 役割は回答の専門性、語彙、観点を調整する補助になる。
- 注意点
  - 「あなたは専門家です」だけでは不十分。
  - 役割を与えただけで質の高い回答が得られるわけではない (https://aclanthology.org/2024.findings-emnlp.888/)
  - 品質を上げる中心要素は、目的、読者、文脈、制約、出力形式、評価基準である。(https://arxiv.org/abs/2409.08775)
  - 役割はタスクに合わせて選ぶ。法律、医療、会計、研究などでは有効な場合があるが、平易な説明では逆効果になることがある。 (https://arxiv.org/abs/2605.29420)

### 2. 成功条件・評価基準を先に定義する

**理由. 何を「良い回答」とみなすかを指定しないと、AIは流暢だが目的から外れた回答を出す可能性があるため。**

- 詳細
  - 回答前に、**正確性、網羅性、簡潔性、根拠、実行可能性、対象読者への適合**などの評価基準を指定する
  - 評価基準を先に示すことで、AIは何を優先すべきか判断しやすくなる。

- 注意点
  - 「高品質にして」「いい感じにして」だけでは評価不能。
  - 評価基準が複数ある場合は、優先順位を付ける。( 例：**正確性 > 根拠 > 網羅性 > 読みやすさ** のように指定する。)

### 3. 複雑問題では段階的に考えさせる

**理由. 複雑な推論では、中間ステップを使うことで問題を構造化しやすくなるため。**

- 詳細
  - CoT(Chain-of-Though)は「途中式を書く」効果に近く、モデルが一気に答えを出すより推論を構造化しやすい。(https://arxiv.org/abs/2201.11903?utm_source=chatgpt.com)
  - 特に算術、常識推論、記号推論などでは、CoTにより性能が改善することが報告
- 注意点
  - CoTを長く出せば常に正答率が上がるわけではない。単純な課題では冗長化し、誤った途中推論を増やす可能性がある。

## 4. 複数案を出し、比較・選定させる

**理由. 1本の回答経路だけだと、初期の誤解や思い込みに引きずられやすいため。**

- 詳細
  - ToT(Tree of Thoughts)は候補を木の枝のように広げて、探索・評価・後戻りしながら解く方法。探索・計画系に強い
  - Self-Consistencyは複数の推論経路を生成し、最も一貫した答えを選ぶ方法。正解が比較的一意な課題で使いやすい。(https://arxiv.org/abs/2203.11171?utm_source=chatgpt.com)
- 注意点
  - ToTは生成コストが高い。

## 5. 大きな問題は小さな問題に分解する(Least to Most Prompting)

**理由. 一度に扱う情報量を減らし、各ステップの失敗を見つけやすくするため。**

- 詳細
  - 大きな問題を小問に分けることで、モデルの作業負荷を下げられる。(https://arxiv.org/abs/2203.11171?utm_source=chatgpt.com)
- 注意点
  - 分解した小問題が間違っていると、後工程に誤りが伝播する。分解結果も人間またはAIレビューで確認する。

### 6. 中間成果物を出させ、人間がレビューできる形にする

**理由. 最終回答だけでは、どこで誤ったかを人間が確認しにくいため。**

- 詳細
  - 答えだけ合っていても途中が誤っている場合がある。途中を確認すれば、どこで壊れたか分かる。(https://arxiv.org/abs/2305.20050?utm_source=chatgpt.com)
  - 何を比較し、なぜ捨てたかが残るため、人間がレビューしやすい。(https://arxiv.org/abs/2305.10601?utm_source=chatgpt.com)
- 注意点
  - 「中間成果物を参考にして最終化」ではなく、**中間成果物を検証してから最終化**と指示する。
  - これはAIの「本当の頭の中」を見ることではなく、**レビュー可能な作業ログを作る**こと。

  - LLMは分解が得意でも計算でミスするため、計算・実行はPython等に任せる方が堅い。(https://arxiv.org/abs/2211.10435?utm_source=chatgpt.com)

### 7. 外部根拠に接続し、AI 自身に「不足情報」を申告させる

**理由. ハルシネーションを減らし、回答の検証可能性を上げるため。**

- 詳細
  - 外部文書を検索して回答に使うモデルは、入力データだけに頼るモデルよりも、知識集約タスクでより事実ベースな生成を行うことが報告されている(https://arxiv.org/abs/2005.11401)
  - 不確かな質問の上位3分の1を棄権させると高品質回答率が80%から90%に、ELI5で67%から80%に改善したと報告されている(https://arxiv.org/abs/2203.11147)
- 注意点
  - 「正確に答えて」「嘘をつかないで」とだけ書いてもハルシネーション対策には効果は薄い(https://learn.microsoft.com/en-us/azure/foundry/openai/concepts/prompt-engineering)
  - 「出典を付けて」とだけ書くだけだと出典が捏造される可能性がある。(https://arxiv.org/abs/2305.14627)

### 8. 出力形式の固定化と例を示す

**理由. 出力結果がぶれなくなる**

- 詳細
  - とくにFew-shot(多く例を示す)はモデルに「このタスクでは何を答えとみなすか」を文脈内で示せるため、Zero-shotよりも出力のブレを抑えやすい(https://aclanthology.org/2022.emnlp-main.759/)
- 注意点
  - 回答内容の品質を上げるものではない。示す例によってはフォーマットバイアスがかかり、品質低下を引き起こす可能性もある(https://arxiv.org/abs/2408.08656)

### 9. 調査・生成プロンプト、レビュープロンプト、修正プロンプトは分けること

**理由. 1つの巨大プロンプトに全工程を詰めると、観点が混ざり、レビューが初期回答に引きずられやすくなるため。**

- 詳細
  - Anthropicも生成→レビュー→修正のプロンプトチェーンを代表例として説明している。
  - 自己選好バイアス(AIが自分の出力や馴染みのある文体を高く評価しやすい)対策(https://arxiv.org/abs/2404.13076?utm_source=chatgpt.com)
  - アンカリングやフレーミングの影響が報告されており、初期回答や過去文脈がレビュー判断の「錨」になる可能性がある(https://arxiv.org/abs/2412.06593?utm_source=chatgpt.com)

- 注意点
  - 初期生成時の会話を入れすぎると、レビューが引きずられる可能性があるためレビュープロンプトには「成果物・評価基準・根拠資料」だけを渡す
  - レビュープロンプトにはルーブリックを必ず入れる(正確性、網羅性、根拠、反例、リスクを固定する。)
  - レビュープロンプトも原則4同様、外部情報に接続させる
  - 修正プロンプトでは「レビュー結果をそのまま反映」ではなく、採用・不採用を判断させる。レビュープロンプトの出力結果誤りの影響を抑えるため

### 10. プロンプト自体もAIにレビューさせる(メタプロンプティング)

**理由. プロンプトの曖昧さ、欠落条件、矛盾、評価基準不足を発見しやすくするため。**

- 詳細
  - 自動生成された命令が人間作成命令と同等以上になるケースを報告(https://arxiv.org/abs/2211.01910?utm_source=chatgpt.com)
- 理由
  - プロンプト同士を比較する場合は位置バイアス(最初に提示した内容を好む)、冗長性バイアス(長い文章を好む)、自己評価バイアス(自分と同じモデル系列で生成された回答を、他系列より高く評価する)に注意し、必ず人間のレビューもはさむこと(https://hatohato.jp/intro/agent_patterns_intro/practice/judge-biases.php)

## 成功条件・評価基準

以下の基準を満たす回答を高品質とみなします。

優先順位は以下の通りです。

1. 目的に合っていること
2. 事実・根拠が正確であること
3. 読者にとって理解しやすいこと
4. 実行・判断に使えること
5. 不確実な点が明示されていること
6. 不要に冗長でないこと

必要に応じて、以下の評価軸で自己確認してください。

| 評価軸       | 説明                                           |
| ------------ | ---------------------------------------------- |
| 目的適合性   | 目的・ゴール・利用場面に合っているか           |
| 読者適合性   | 想定読者の知識量・関心・立場に合っているか     |
| 正確性       | 事実、定義、数値、引用、前提に誤りがないか     |
| 網羅性       | 必要な観点が不足していないか                   |
| 具体性       | 抽象論だけでなく、実例・手順・判断材料があるか |
| 実行可能性   | 読者が次の行動に移せる内容になっているか       |
| 根拠の明確さ | 主張と根拠が区別され、確認可能になっているか   |
| 論理整合性   | 前提、理由、結論に矛盾がないか                 |
| 簡潔性       | 重要でない情報に分量を使いすぎていないか       |
| リスク配慮   | 誤解、失敗、例外、不確実性に触れているか       |
| 表現品質     | 読みやすく、誤字脱字や表記ゆれが少ないか       |

必要に応じて、タスク固有の評価軸を追加してください。

## 検討手順

以下の手順で進めてください。

1. 依頼内容を実行するために必要な前提情報を整理する
2. 不明点・確認が必要な点を洗い出す
3. 目的に対して有効そうな案を複数出す
4. 各案を評価軸に従って比較する
5. 比較が難しい場合は、案を小さな構成要素に分解して再評価する
6. 明らかに不適切な案は、非推奨理由を明示して棄却する
7. 最終的に推奨度の高い案を選定する
8. 採用理由、リスク、追加確認事項をまとめる
9. 指定フォーマットに従って最終成果物を作成する

## 注意事項

以下のルールを守ってください。

- 不明な情報がある場合は、勝手に断定しない
- 推測する場合は「推測」と明記する
- 根拠が弱い情報は「根拠弱」と明記する
- 確認が必要な情報は「要確認」と明記する
- 判断できないものは「不明」または「判定保留」とする
- 最新性が重要な情報は、可能な限り公式情報、一次情報、標準仕様、査読論文、信頼できる資料を優先する
- 二次情報や個人ブログは補助情報として扱う
- 数値、日付、固有名詞、法令、仕様、価格、ツール情報などは特に慎重に扱う
- 中間成果物は、AIの内部思考ではなく、人間が確認できる作業ログとして出力する
- 最終成果物を出す前に、中間成果物の前提・比較・不明点を確認する

## レビュー方針

以下の方針でレビューしてください。

1. 良い点よりも、修正すべき点を優先して指摘する
2. 問題がある箇所は、なぜ問題なのかを説明する
3. 問題が発生する条件を明示する
4. 可能な限り、具体的な修正案を示す
